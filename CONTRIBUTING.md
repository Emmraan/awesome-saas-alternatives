# Contributing to Awesome SaaS Alternatives

Thanks for considering a contribution! This project is a community-driven
directory of free, open-source, self-hosted and lower-cost alternatives to
popular paid SaaS. GitHub is the CMS: every product lives in `data/products.json`
and the site is generated from it.

**TL;DR:** fork → branch → make a focused change → run the checks → open a PR.
Untested PRs will be rejected.

---

## Code of Conduct

This project has a [Code of Conduct](CODE_OF_CONDUCT.md). By participating you
agree to uphold it. Report unacceptable behavior to the maintainers.

## Security

Found a vulnerability? Do **not** open a public issue. Follow the disclosure
process in [SECURITY.md](SECURITY.md).

## What you can help with

- **Adding or editing products** — the most common contribution. See
  [Adding a product](#adding-a-product).
- **Fixing a bug** in the site (Next.js/React/Tailwind) or in the data pipeline.
- **Improving search/categories** in `lib/`.
- **Docs** — this file, the README, or `docs/`.
- **Triage** — confirming reported issues and verifying proposed alternatives.

Open issues are a good place to find work.
For larger features, open an issue first and discuss before building.

## Local setup

Prerequisites: **Node.js 22+** (see `.nvmrc`) and **pnpm** (see `packageManager`
in `package.json`; corepack is recommended: `corepack enable`).

```sh
pnpm install        # install dependencies
pnpm dev            # start the dev server at http://localhost:3000
```

`.env.example` documents the environment variables you may need. Copy it to
`.env.local` for a local build that requires `NEXT_PUBLIC_SITE_URL`.

### Useful commands

| Command                | What it does                                      |
| ---------------------- | ------------------------------------------------- |
| `pnpm dev`             | start the Next.js dev server                      |
| `pnpm build`           | production build (needs `.env.local`)             |
| `pnpm start`           | serve the production build                        |
| `pnpm lint`            | ESLint over the whole repo                        |
| `pnpm typecheck`       | TypeScript type-check (incremental)               |
| `pnpm test`            | run the Vitest suite                              |
| `pnpm test:coverage`   | run tests + `lib/` coverage gate (≥80%)           |
| `pnpm validate-data`   | validate all `data/*.json` against the schemas    |
| `pnpm sync:github`     | refresh GitHub stars/forks/license/release data   |

## Project structure

```
app/            Next.js routes (App Router)
components/     React components (ui/ + page-specific)
data/           JSON data — categories, features, products (the "CMS")
lib/            pure logic: types, schemas, search, directory, seo
scripts/        Node/tsx scripts: validate-data, sync-github
tests/          Vitest suite (data, logic, components)
```

`lib/schemas.ts` is the single source of truth for the data shape (zod).
`scripts/validate-data.ts` enforces it — run it after any data change.

## Git workflow

- Cut a feature branch from the latest `main` (`git checkout -b feat/my-change`).
- Commits follow **[Conventional Commits](https://www.conventionalcommits.org)**:
  `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `ci:`, `chore:` …
  These drive the semantic-release changelog and version bumps, so keep them accurate.
- Keep PRs small and single-purpose. Squash on merge (the maintainers will squash
  if needed).
- Don't edit `CHANGELOG.md` by hand — it is auto-generated by semantic-release.

## Tested-PR rule

Untested PRs will be rejected. Before opening a PR, make sure:

1. `pnpm lint` passes (0 errors, 0 warnings on your files).
2. `pnpm typecheck` passes.
3. `pnpm test` passes — and for changes touching `lib/`, `pnpm test:coverage`
   still meets the ≥80% gate.
4. For data changes, `pnpm validate-data` passes.

Describe how you tested your change in the PR description.

## Adding a product

Products live in `data/products.json`. Each entry must match `productSchema`
(see `lib/schemas.ts`). A minimal entry looks like:

```json
{
  "slug": "coolify",
  "name": "Coolify",
  "tagline": "Open-source, self-hostable PaaS",
  "description": "Self-host your apps, databases and services on your own servers.",
  "website": "https://coolify.io",
  "repo": "coollabsio/coolify",
  "license": "Apache-2.0",
  "openSource": true,
  "selfHosted": true,
  "pricing": "free",
  "difficulty": "medium",
  "categories": ["cloud-hosting", "serverless"],
  "replaces": ["Vercel", "Netlify"],
  "features": ["self-hosted", "open-source", "docker"],
  "tags": ["paas", "deployment"],
  "github": null,
  "createdAt": "2026-08-19T00:00:00.000Z",
  "updatedAt": "2026-08-19T00:00:00.000Z",
  "status": "active"
}
```

Rules:

- `slug` is lowercase kebab-case and unique.
- `replaces` entries must match the **name** of an existing product in the same
  file (case-insensitive).
- `categories` and `features` must reference existing slugs/ids in
  `data/categories.json` and `data/features.json`.
- Set `github` to `null` in your PR. **Do not invent GitHub stats** — the
  `sync:github` script fetches real stars/forks/license/release data from the
  GitHub API and fills this in.

### Refreshing GitHub metadata

After a PR with a new `repo` lands, or whenever the numbers look stale:

```sh
GITHUB_TOKEN=your_token pnpm sync:github
```

The script is idempotent: it only refetches repos whose metadata is older than
24 hours (or everything with `--force`), and it skips repos with no `repo`
field. Without a token you are limited to 60 requests/hour; with a token the
limit is 5000/hour. See `.env.example`.

## Opening a pull request

1. Push your branch and open a PR against `main`.
2. Fill in the PR description: what changed, why, and how you tested it.
3. CI runs lint, typecheck, tests (with coverage gate) and `validate-data`
   automatically for PRs touching code or data. Wait for green before pinging.
4. Keep the PR focused. If it gets big, split it.

## Reviewing

- Be kind and specific; prefer suggestions over commands.
- Verify the claimed testing rather than assuming it.
- Flag untested changes — the tested-PR rule applies to everyone.

## Releasing

Releases are automatic: when a conventional-commit PR merges to `main`,
semantic-release derives the next version, writes the changelog, and creates a
GitHub release. You never bump versions or edit the changelog by hand.
